## B. NON-NEGOTIABLE RULES

### B.1 Passive-only (violations = task failure)
The system must never: send/inject/replay packets onto any network; open TCP handshakes; probe/scan; resolve or contact observed domains/IPs (no DNS lookups of observed names, no WHOIS, no reputation API calls); mitigate/block; decrypt TLS/QUIC; execute malware; assume a return path. PCAP files are read from disk into the **in-process** pipeline only. "Simulated ingest/replay" in this order means feeding parsed `PacketEvent`s to the in-process pipeline — never to a network interface.

## C. KNOWN DEFECTS IN THE CURRENT PHASE 7B CODE (you must fix in Stage 1)

These were found by reading the delivered `dataset/schema.py`, `adapter.py`, `validation.py`, `cic_adapter.py`, `ctu_adapter.py`, `tests/test_dataset.py`, `docs/phase_7b_audit.md`. Verify each against the real code, then fix; add a regression test for each.

1. **Magic-number `byte_ratio`.** Adapters hard-code `10000.0` when reverse bytes = 0. Phase 6 explicitly rejected ad-hoc conventions (`byte_ratio = fwd_bytes` is forbidden). There must be **one** shared function `compute_byte_ratio(fwd, rev)` and one named constant, used by `processing/features.py`, both adapters, and ML preprocessing. Convention (unless Phase 6 already committed a *documented and tested* alternative, in which case adopt that and adapt adapters): `rev>0 → fwd/rev`; `rev==0 and fwd>0 → BYTE_RATIO_CAP` (named constant, 1e4); `rev==0 and fwd==0 → 0.0`; always `min(ratio, CAP)`. `is_unidirectional` already disambiguates. ML preprocessing applies `log1p`. Document in `docs/features.md`.
2. **Silent timestamp fallback to `0.0`** on parse failure (both adapters), and validation only flags `timestamp < 0`. This fabricates data. Replace with reject-and-count (see Stage 1).
3. **Timezone nondeterminism.** `datetime.strptime(...).timestamp()` interprets naive times in the machine's local timezone → results differ between machines. Parse as UTC explicitly and document that only relative ordering is meaningful.
4. **Wrong window semantics.** CIC `Timestamp` and CTU `StartTime` are flow **start** times, but adapters set `window_end = timestamp` and `window_start = timestamp - duration` (i.e., the flow appears to start before it did). Fix: `flow_start = parsed time`, `flow_end = flow_start + duration`, `timestamp = flow_start` (document), and validation must check `flow_start <= flow_end`.
5. **CTU-13 labels are mapped incorrectly.** `background` → BENIGN is wrong: CTU-13 "Background" traffic is **unlabelled**, not verified benign. `botnet` → C2_BEACONING for everything is wrong: `From-Botnet-…-SPAM`, `…-UDP-DNS`, click-fraud, port-scan-by-bot are not C2 beaconing. Hard-coded substring matching must be replaced by an explicit, reviewable, config-driven label map (Stage 1).
6. **Incorrect claim in `phase_7b_audit.md`:** "cannot compute src-IP context features from CTU-13 CSV". CTU-13 *has* `SrcAddr`, `DstAddr`, `Dport`; the three `src_ip_*` features **can** be computed with a record-level windowed aggregator using the same definitions as Phase 6. Only CIC-IDS2018 (AWS "TrafficForML" CSV: no IPs) truly lacks them. Correct the audit doc.
7. **Byte-count semantic mismatch not addressed.** CICFlowMeter `TotLen Fwd/Bwd Pkts` are **payload** bytes; CTU `TotBytes/SrcBytes` include headers; Phase 4 uses whatever Phase 3 records as packet length. Audit what Phase 3's `length` actually is (Scapy `len(pkt)` includes Ethernet). Either align (CIC: add `Fwd/Bwd Header Len`) or document the mismatch and **exclude absolute byte-magnitude features from cross-source models**. Likewise flow-termination semantics differ (CICFlowMeter splits on FIN and a 120 s timeout; check what `processing/flow.py` does). Document; never claim equivalence you did not test.
8. **Adapter robustness gaps.** No handling of embedded repeated header rows, NaN/Infinity (e.g., `Flow Byts/s`), negative durations/counts, duplicate rows, empty `Label`, whole-file memory use, or CTU `Dir`. Loading is streaming only (no full-file `list()`).
9. **Weak tests.** `test_group_aware_splitting_and_reproducibility` asserts nothing about splitting; `test_no_fabricated_values` is trivially true. Replace with tests that would actually fail on the bugs above. No test may read real dataset files (use tiny fixture CSVs written under `tmp_path`).
10. **Train/serve skew risk (design issue).** Models trained on CSV-derived rows and deployed on PCAP-derived streaming features will silently mismatch. Resolve with the two-path architecture in Stage 4: one feature registry, one definition per feature, availability masks per source, models trained/served per **feature profile**.

## E. CROSS-CUTTING ENGINEERING CONTRACTS

E.1 **Detection units.** Two entity types per window (default window 10 s, slide 1 s; configurable):
- **Source-centric entity-window** `(window_end, src_ip)`: scanning, exfiltration, C2, DGA/DNS tunnelling, encrypted-malware sessions.
- **Destination-centric entity-window** `(window_end, dst_ip)`: DDoS (many sources → one victim looks benign per-source).
Flow-level rows remain the evidence layer; every alert lists representative `flow_id`s.

E.2 **Labels for entity-windows.** Attack if the attack-labelled packet (or flow) share of that entity in the window ≥ 0.5; Benign if the attack share == 0; windows with 0 < share < 0.5 are `ambiguous`: excluded from training and threshold-fitting, counted and reported.

E.3 **Leakage control.** Sliding windows overlap 90% → random row splits leak. Split by **scenario/capture** wherever ≥ 2 scenarios exist; otherwise chronological blocks with an **embargo** ≥ window length + max flow duration on each boundary (drop straddling records). Test set is touched exactly once, after thresholds/hyperparameters are frozen on validation. Split manifests are saved (JSON with row/scenario ids + hash) and re-verified by a test.

E.4 **No future-window leakage** in features: a feature at window end `t` uses only packets with timestamp ≤ `t`. Baseline statistics (per-host median/MAD, benign bigram model, scalers) are fit on the training split only.

E.5 **Feature registry** (`ml/feature_registry.py`): single source of truth listing per feature: `name, family, dtype, unit, definition, edge_case_convention, threat_relevance, availability{pcap, ctu13, cic2018}, entity_type`. `docs/features.md` is **generated** from it by `scripts/gen_feature_docs.py`; a test asserts registry ⇔ implemented columns match exactly. Missing-because-unavailable is `NaN`/`None` with an availability mask; never `0.0` fabrication.

E.6 **Feature profiles.** `flow_core` (Phase 6 16 + shared derived), `entity_window` (fan-out/volume/asymmetry), `beacon` (long-horizon channel timing), `dns`, `tls`. Each detector declares the profile it needs. A model is trained only on sources that supply its profile. Produce a machine-generated **coverage matrix** (`reports/coverage_matrix.json` → `docs/data_coverage.md`): for each threat × profile, which sources (synthetic/CTU/CIC) supplied training, validation, and test data, with row counts. This is the honest statement of what was trained on real vs synthetic data.

E.7 **Forward compatibility (do not implement, only preserve).** The team's later "Cyber Threat Digital Twin" layers (dynamic communication graph, Threat DNA, baseline-integrity, attack storyline, temporal world model / K-step simulation, counterfactuals, blast radius) will consume: chronological entity-window tables with `src_ip`/`dst_ip` retained (graph-ready), alerts carrying window bounds and per-window score vectors, and an optional static `mitre_stage`. Keep these fields; build none of those layers now.

### STAGE 7 — Confidence, severity, evidence, structured alerts (Phase 10)

7.1 **Alert schema** (`detection/alert.py`, pydantic or dataclass + `docs/alert_schema.json` generated): `alert_id`, `incident_id`, `timestamp` (capture time, epoch float + ISO-8601 UTC), `window_start`, `window_end`, `flow_id` (primary) and `flow_ids` (≤ 10 representative), `src_ip`, `dst_ip`(s), `threat_class`, `is_unknown`, `confidence` (calibrated prob in [0,1]), `severity` (`LOW|MEDIUM|HIGH|CRITICAL`), `severity_score` (0–100), `severity_components`, `evidence[]`, `model_id`, `feature_profile`, `provenance` (`SYNTHETIC_LAB|REAL_CTU13|REAL_CIC2018|LIVE_OR_UNLABELLED_PCAP`), optional `mitre_stage` (static lookup only: Recon→Reconnaissance, C2/DGA→Command and Control, Exfil→Exfiltration, DDoS→Impact, encrypted malware→Command and Control; **no prediction**), `schema_version`.
7.2 **Severity** (`detection/severity.py`): documented, deterministic, unit-tested formula: `score = 100 * clip( w_class * (0.45*conf + 0.30*magnitude + 0.15*persistence + 0.10*breadth), 0, 1 )` where `magnitude` is the threat-specific measured quantity normalised by the **training-attack robust percentile (p95)** (DDoS: pps/source count; recon: unique ports/hosts; exfil: outbound bytes; C2: channel count/periodicity; DGA: unique-domain rate; TLS: session anomaly), `persistence = min(1, window_count / P)`, `breadth` = affected destinations/sources normalised, `w_class` a documented per-class weight table in config. Bands: LOW <35, MEDIUM 35–60, HIGH 60–80, CRITICAL ≥80 (config). Test monotonicity (↑confidence/magnitude/persistence never lowers severity), bounds, determinism, and that severity ≠ confidence (same confidence, different magnitude ⇒ different severity). If you change constants, document the reason; do not tune them to make demos "look" severe.
7.3 **Evidence** (`detection/evidence.py`): per-threat templates that render **only from measured values** in the window/flow data and explainability output, each item `{type, text, feature, value, benign_reference, flow_ids?}`, e.g. `1 source contacted 137 unique destination ports in 4.2 s`, `129 of 137 connections were short-lived (<1 s)`, `beacon interval median 60.1 s, CV 0.04 over 14 connections`, `avg DNS label entropy 4.1 bits vs benign median 2.9`, `9.8 GB outbound vs 0.4 GB benign-host median (robust z 11.2)`. Every number in evidence text must be computed; a test builds evidence from a fixture and asserts each rendered number equals the source value; a test asserts evidence is never emitted for a feature that was `NaN`/unavailable.
7.4 Wire Stage 6 incidents → alerts. Write alerts as JSONL and expose `AlertStore` (ring buffer + optional append-only JSONL, bounded).
7.5 Tests: schema validation of every alert from the end-to-end runner; required PS-145 fields present (`timestamp`, `flow_id`, `threat_class`, `confidence`, `evidence`); severity/evidence tests above; alert IDs deterministic for identical input.
